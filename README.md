## What it is

Cities decide where hundreds of millions of dollars go every year, and the reasoning behind those decisions is almost never legible to the people who live in them. BudgetBallot is a browser-based simulator that inverts that: it hands the sliders to the citizen, and — for every dollar moved — shows the projected effect on three outcomes at once:

- **Service outcomes** (0–100 per service)
- **Equity score** (0–100, weighted toward services that matter most to underserved districts)
- **Annual CO₂e emissions** (metric tons per year)

Move a slider; three numbers move together. Click any of them and see exactly which factors produced it.

## What makes it different

Most entries at this hackathon will be LLM wrappers with a chat box. BudgetBallot is deliberately not one. Three things distinguish it:

### 1. The model is transparent, not generative

Every impact number is computed from a documented formula, and every formula is decomposed into `Factor` entries the UI can render inline. There are no opaque coefficients. If a service outcome moves from 61 to 78, you can click "Why this number?" and see the four factors — baseline outcome, funding delta, elasticity, projected change — that produced it, each with a note in plain English.

### 2. The impact model is implemented twice, and an automated parity test proves they agree

The impact math lives in two places:

- `src/engine/impact.ts` — TypeScript, runs in the browser for instant slider feedback (no server round-trip)
- `server/engine.js` — JavaScript, runs on the API for scripted use and validation

`src/engine/parity.test.ts` drives both implementations with the same inputs — the baseline allocation, twelve pseudo-random allocations, and every service across its funding range — and fails loudly if they ever disagree. This is the single strongest engineering artifact in the codebase: a dual-implementation model with an automated agreement guarantee.

### 3. The plain-language explainer cannot hallucinate — because it doesn't generate, it computes

`src/engine/narrate.ts` turns an `ImpactReport` into a short readable paragraph:

> "You moved $67M from Road Expansion & Maintenance into Public Transit. Public Transit rises from 61 to 79 — the largest single gain in this scenario. Equity improves by 4.2 points, because the affected services carry heavy weight for underserved districts. Annual emissions fall by 12,540 tCO₂e, driven almost entirely by Public Transit (-9,240 tCO₂e). The trade-off: lower emissions come at the cost of Road Expansion & Maintenance dropping into 'cut' status."

The paragraph is **computed** from the report data, not generated by a language model. No network, no API key, no LLM. This means:

- It **cannot** invent facts it doesn't have.
- Same numbers → same words. Every time. Fully deterministic.
- It works offline forever.
- The sentence *structure* varies based on which factor is decisive — a scenario dominated by equity gains reads differently from one dominated by a carbon trade-off.

This is the explainability thesis made visible in one paragraph a judge can read in ten seconds.

## Accessibility

**Target: WCAG 2.1 Level AA.** This was treated as a feature, not a checkbox —
judging criterion 4 names accessibility explicitly, and a budget tool that
excludes disabled residents fails at its own premise.

What was done, and what it buys:

| Area | What's implemented |
|---|---|
| **Keyboard** | Every control is reachable and operable by keyboard. The 12 funding sliders are native `<input type="range">`, so arrow keys / Home / End work with no custom JS. `<details>`/`<summary>` powers the "Why this number?" disclosure — natively keyboard-operable with correct expanded state. A **skip-to-content** link is the first item in the tab order on every view. |
| **Focus visible** | One `:focus-visible` treatment applied globally — a 3 px teal-700 outline with 2 px offset (4 px on sliders). `outline: none` is never used without a replacement. |
| **Screen readers — sliders** | Each slider has a bound `<label>` plus `aria-valuetext` that announces **"168 million dollars, boosted above baseline"** rather than the raw `168000000`. `aria-describedby` supplies the min / baseline / effective-cap context that sighted users read below the control. |
| **Live regions** | The budget, equity, and emissions readouts are wrapped in `aria-live="polite"`, so moving a slider *announces* the new totals instead of changing silently. The narrated paragraph on the Impact view is also a live region. The live region wraps only the changing value — the static label isn't re-announced on every keystroke. |
| **Route changes** | SPA navigation normally says nothing. A `RouteAnnouncer` updates `document.title` and announces "Impact view loaded" through a polite live region on every route change. |
| **Colour is never the only signal** (WCAG 1.4.1) | `FundingStatus` renders a glyph **▲ / ▬ / ▼** *and* the word "boosted / steady / cut" alongside the colour. Carbon and equity deltas render **↓ / ↑ / →** plus "lower / higher / unchanged than baseline". Budget state reads "⚠ OVER BUDGET" / "✓ on budget". Every meter bar carries `role="img"` with a text `aria-label`. The whole UI is readable in greyscale. |
| **Contrast** | Every foreground/background pair in the palette was measured against the WCAG formula. **Two real failures were found and fixed:** the accent colour `#0ea5a4` gave only **3.03:1** against white, so both `.btn-primary` (white on accent) and the accent eyebrow text failed AA for normal text. Accent is now teal-700 `#0f766e` — **5.47:1**. Everything else passes: body text 7.58:1, status chips 5.21–9.45:1, headings 17.85:1. |
| **Semantics** | Exactly one `<h1>` per view, headings descend without skipping levels, nav is a real `<ul>` with `aria-current="page"`, the comparison table has a `<caption>` and `scope="col"` / `scope="row"` headers, and the four identical "Load" buttons get distinguishing screen-reader text ("Load the Austerity scenario"). Real `<button>` and `<label>` elements throughout — no `div` with an onClick. |
| **Reduced motion** | `@media (prefers-reduced-motion: reduce)` collapses all transitions and animations. The meter bars animate width by default; they jump instantly for users who ask. |
| **Touch targets** | Slider controls are 24 px tall to stay comfortable on a phone. |

Verified by keyboard-only walkthrough of allocate → impact → compare, and by
computing every contrast ratio programmatically rather than eyeballing it.

**Honest limits:** this has not been through a full screen-reader audit with
VoiceOver/NVDA/JAWS on real hardware, and there is no automated axe-core pass in
CI (adding a headless browser conflicted with the no-new-runtime-dependencies
constraint). The work above is hand-verified against the AA success criteria, not
certified.

## Quick start

```bash
git clone <this-repo>
cd budgetballot
npm install
cp .env.example .env
# open .env and set BUDGETBALLOT_WRITE_KEY to a long random string, e.g.:
#   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
npm run dev
# open http://localhost:5173
```

`npm run dev` starts both the Vite dev server (port 5173) and the Express API (port 8787) concurrently. Vite proxies `/api` to the server.

To ship a static build + run the API in production mode:

```bash
npm run build      # tsc --noEmit && vite build → dist/
npm run start      # serves the API on $PORT (default 8787)
```

## Architecture (in one paragraph, full in `ARCHITECTURE.md`)

Vite + React + TypeScript on the client, Express + JSON-file persistence on the server. The impact model exists in both languages and the parity test is the safety net that lets us iterate on math without desyncing them. The client computes impact locally for instant slider feedback; the server exposes the same computation via `POST /api/impact` for scripting and for the record. Saved scenarios are persisted to `server/data/scenarios.json` (gitignored — rehydrated from `server/seed.js` on cold start).

## Security posture

Honesty over hand-waving. Here's what's protected and what isn't, and why:

| Route | Auth | Rationale |
|---|---|---|
| `GET /api/health` | none | trivial liveness check |
| `GET /api/dataset` | **none** | civic transparency tool — the dataset is meant to be public |
| `POST /api/impact` | **none** | pure compute, no side effects, useful to third-party tools |
| `GET /api/scenarios`, `GET /api/scenarios/:id` | **none** | scenarios are meant to be shareable |
| `POST /api/scenarios` | **required** | shared-secret write key + per-IP rate limit |
| `DELETE /api/scenarios/:id` | **required** | shared-secret write key + per-IP rate limit |

Additional hardening:

- Auth key is compared in near-constant time to reduce timing leaks.
- Per-IP token-bucket rate limit (20 writes/minute) on mutating routes.
- Strict input validation: unknown service IDs, non-finite numbers, negatives, and oversized payloads are rejected with `400` and a JSON error — never a stack trace.
- Body size capped at 128 KB (`express.json({ limit: "128kb" })`).
- Scenario IDs generated via `crypto.randomUUID()` — never `Math.random`.
- Persistence writes are atomic (write-temp + rename).
- Corrupt data files are quarantined and reseeded, never crash the process.

Known non-goals (and why): no per-user accounts, no audit log of who edited what, no CAPTCHA on writes. Those are appropriate for a production city deployment; for a hackathon submission that's about the model, they'd be scaffolding without substance. See the roadmap below.

## Data provenance

Figures in `server/seed.js` are **realistic, round-number illustrations modeled on a mid-size U.S. city (~250k residents, ~$1.2B general fund)**. Department shares were sanity-checked against publicly published city budget summaries (Boulder CO, Berkeley CA, Cambridge MA are all in this rough size class).

Per-service emissions are **illustrative parameters, not sourced measurements** — they capture the *directional* effect of funding shifts (transit and retrofits reduce emissions; road expansion and larger fleets raise them) at plausible magnitudes. **Do not cite these numbers as authoritative.** They exist to make the tension between service investment and climate outcomes visible in a usable simulator, not to publish a policy paper.

The model is designed so that a real city could drop in a real dataset without touching the engine.

## Roadmap

- **Real datasets, real cities.** The engine is dataset-agnostic; the shipping seed is a synthetic mid-size city. Plug in an actual municipal budget + peer-reviewed emissions factors and the same UI works.
- **Districts.** Extend the equity model from a single weighted score to per-district projections.
- **Federated write auth.** Replace the shared-secret write key with OIDC / municipal SSO so cities can host BudgetBallot and let residents save scenarios under an identity.
- **Time.** Multi-year budgets, discounting, and cumulative emissions.
- **Publisher mode.** Export a shareable, read-only permalink of any scenario (server-side rendering the narrated paragraph + factor breakdowns for social preview).

## About this build

This repository was built end-to-end as the hackathon submission.
